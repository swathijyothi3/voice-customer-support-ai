# Voice Customer Support AI — Intent Routing

**Problem:** Customer support systems receive large numbers of user requests. Instead of
manually reading and routing every request to the right team, this project automatically
determines which **category** a spoken request belongs to — in real time, via voice.

```
Speech → Text → Preprocessing → TF-IDF Vectorization → Logistic Regression → Category + Confidence
```

## How to run it

```bash
pip install -r requirements.txt
streamlit run app.py
```

Notes:
- **PyAudio** (needed for microphone access) can be tricky to install:
  - Windows: `pip install pyaudio` usually works directly.
  - Mac: `brew install portaudio` first, then `pip install pyaudio`.
  - Linux: `sudo apt install portaudio19-dev python3-pyaudio` first.
- No microphone available? Use the **"Type instead"** tab — identical pipeline, typed input.
- Speech-to-text uses the free Google Web Speech API, so the mic tab needs internet access.

To retrain from scratch:
```bash
cd notebooks
jupyter notebook model_building.ipynb
# run all cells -> regenerates everything in ../models/
```

## The dataset

**Bitext Customer Support Training Dataset** (downloaded from Hugging Face) — 26,872 real,
publicly available customer-support requests, each labeled with:
- `category`: 11 broad classes (ACCOUNT, ORDER, REFUND, INVOICE, CONTACT, PAYMENT, FEEDBACK,
  DELIVERY, SHIPPING, SUBSCRIPTION, CANCEL) — **this is what the model predicts**
- `intent`: 27 fine-grained classes (e.g. `cancel_order`, `track_refund`) — not used here, but
  a natural next step if you want a harder version of this project later

**Worth knowing for interviews:** this dataset is itself template-generated by Bitext (that's
*why* it's clean, balanced-ish, and easy to label at scale) — real customer messages in
production would be messier and less separable. That's part of why the model hits ~99% accuracy;
it's a legitimate, widely-used dataset, but the number should be read as "this task is learnable
from this data," not "this system is 99% accurate on arbitrary real-world speech."

The dataset also contains template placeholders like `{{Order Number}}` — a real customer would
never say those words aloud, so `src/preprocessing.py` strips them out before vectorization. This
is a good detail to mention in an interview: it shows you actually inspected the data rather than
blindly running a standard pipeline.

**A naming trap worth knowing:** `CANCEL` in this dataset does **not** mean "cancel my order" —
it specifically means cancellation *fees*/termination *penalties* (e.g. "check the early
termination fee"). Actually cancelling a purchase is labeled under `ORDER` instead (e.g. "help
canceling purchase {{Order Number}}"). So if you say "I want to cancel my order" and the app
routes it to `ORDER`, that's correct per this dataset's own taxonomy, not a misclassification —
verify this yourself by filtering `dataset.csv` for `category == "CANCEL"` and reading a few rows.
This is worth mentioning proactively in an interview: it shows you validated label meanings
against the data instead of assuming from the category name.

## Results

- Baseline (untuned) test accuracy: **99.2%**
- Tuned (`GridSearchCV`, best `C=10`) test accuracy: **99.3%**
- Classes are imbalanced (ACCOUNT: 5,986 rows vs CANCEL: 950 rows) — per-class F1-scores in the
  notebook confirm the model isn't just doing well on the majority class.

## Explaining this project in an interview (short version)

> "I built a system that takes a spoken customer support request and automatically routes it
> to the correct department — Account, Refund, Shipping, and so on — instead of a human reading
> every ticket. I used a real, published customer-support dataset with about 27,000 labeled
> requests. On the backend, I cleaned the text — including stripping out dataset-specific
> template placeholders I noticed during EDA — converted it to TF-IDF features with unigrams
> and bigrams, trained a Logistic Regression classifier, and tuned it with GridSearchCV. The
> app also shows the model's confidence and its top-3 candidate categories, which matters in a
> real routing system: if confidence is low, you'd want a human to double-check instead of
> auto-routing blindly."

### Likely follow-up questions and how to answer them

**Q: Why predict `category` instead of the more granular `intent`?**
Category (11 classes) is the right level for automatic *routing* — it maps cleanly to support
team structure (billing team, shipping team, etc.). The finer-grained `intent` (27 classes) is
available in the same dataset and would be a natural next iteration if the business wanted more
granular automation, like pre-filling a specific response template.

**Q: 99% accuracy seems very high — is that realistic?**
Be upfront: the dataset is template-generated, so classes are quite linguistically distinct and
the task is easier than messy real-world support tickets would be. I'd expect real production
accuracy to be lower, and I'd want to validate against real historical tickets before deploying
this as-is. High accuracy here mainly demonstrates the pipeline works correctly end-to-end.

**Q: Why TF-IDF instead of embeddings/transformers?**
TF-IDF with bigrams is fast, fully interpretable, and worked very well here because support
requests use fairly consistent, domain-specific vocabulary per category. For messier real-world
text, or if I wanted to catch semantic similarity ("I want my money back" vs "issue me a refund"
without those bigrams overlapping), I'd move to Sentence-BERT embeddings feeding the same
classifier — same architecture, different feature extraction step.

**Q: How do you handle a low-confidence prediction?**
The app shows the top-3 candidate categories with their probabilities, not just the top pick.
In a real deployment, I'd set a confidence threshold below which the ticket goes to a human
triage queue instead of being auto-routed.

**Q: What would you add with more time?**
Predicting the finer-grained `intent` field as a second-stage classifier once category is known,
and validating against real (non-templated) support tickets to get an honest accuracy estimate.
